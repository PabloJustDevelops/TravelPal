# Internationalization and locale detection

Issue: [#131](https://github.com/PabloJustDevelops/TravelPal/issues/131)

## Summary

Deliver Spanish and English for all first-party interface and legal copy, locale-aware formatting, persistent language choice, static locale routes, and language-specific SEO. Do not translate user-authored content, third-party provider content, or repository documentation. Do not add runtime language negotiation to the Worker.

## Verified current state

- `AGENTS.md`, `CONTEXT.md`, and `docs/ARCHITECTURE.md` specify `output: "export"` and an assets-only Cloudflare Worker. Production has no middleware, Next server, or route handlers.
- `src/app/` contains unprefixed routes. The UI and legal copy are Spanish; there is no catalog or i18n framework. Examples include `src/components/calendar/Calendar.tsx`, `src/components/tasks/TaskCard.tsx`, and `src/components/legal/LegalPage.tsx`.
- `public/_redirects` contains unprefixed redirects.
- `scripts/build-seo.mjs` writes a fixed sitemap; `scripts/check-seo.mjs` hard-codes indexable and private routes and validates canonical URLs; `scripts/validate-static-export.mjs` checks required exported paths.
- `playwright.config.ts` runs the `smoke` and serialized `flows` projects. `jest.config.js` uses Jest/Testing Library and global coverage thresholds.
- `docs/DECISIONS/ADR-009-camino-unico-sdk-en-navegador.md` and ADR-014 prohibit bringing application data through a BFF or adding a Next runtime to production.

## Approach

Use static locale-prefixed routes (`/es/...` and `/en/...`) and a shared message catalog in TypeScript. Add a locale layout/provider that resolves messages from the route, and locale-aware date/number formatting. Keep `/` as Spanish-compatible static fallback, with a small client bootstrap that reads saved preference then `navigator.language` and navigates to the matching static route after hydration. Persist an explicit user selection. This avoids claiming that `Accept-Language` can be read by the assets Worker and avoids locale-dependent server HTML/hydration.

Generate both locales for every supported page with the Next 16 static export conventions documented in the installed `node_modules/next/dist/docs/` before implementation. Keep direct links and redirects locale-aware. Index only public landing, auth-entry, and legal pages; authenticated pages remain `noindex` and excluded from the sitemap. Emit `hreflang` alternates and self-canonicals for public localized pages.

Discarded: middleware/Worker negotiation (not present in static hosting); a browser-only text swap over one route (duplicates translation logic and cannot provide correct static SEO); a third-party translation service (runtime dependency and inconsistent/legal copy).

## Concrete changes

### Phase 1: route and catalog foundation

- Add locale types, message dictionaries, fallback rules, and formatting helpers under `src/lib/i18n/`.
- Add static locale route segments under `src/app/[locale]/` for the existing route set; use `generateStaticParams` only if supported by the installed Next 16 export guide. Preserve auth callback semantics and query parameters.
- Move shared shell and page copy behind typed message keys. Translate every first-party public, authenticated, accessibility, validation, and legal string; leave stored user data untouched.
- Update navigation, links, forms, dialogs, empty/error/loading states, Storybook stories, and date-fns locale selection.
- Decide whether to retain unprefixed routes as compatibility aliases or redirects; implement static redirect behavior in `public/_redirects` where possible.

### Phase 2: preference and SEO

- Add a client-side locale bootstrap and language selector. Preference order: saved explicit selection, browser language, then Spanish. Do not vary server-rendered content based on browser headers.
- Update `scripts/build-seo.mjs` to produce localized sitemap entries and static OG copy/assets as needed.
- Update `scripts/check-seo.mjs` to validate the exact localized public route set, canonical self-reference, reciprocal `hreflang`, and no cross-locale canonical. Update robots rules only for newly introduced route shapes.
- Update `scripts/validate-static-export.mjs` to check critical routes for both locales while retaining private-key leak checks.

### Phase 3: regression coverage

- Add unit tests for locale parsing, fallback, preference precedence, formatting, and message-key completeness.
- Add export/SEO fixtures for missing locale files, links, canonical, sitemap, and redirects.
- Add a Playwright locale flow and a critical authenticated flow in English; add Storybook accessibility coverage for both message providers.

No database migration, RLS change, InsForge function, or server endpoint is required.

## Tests

- Jest: locale resolver, storage/bootstrap, formatting, dictionary completeness, and translated component behavior.
- Export gates: `pnpm run build`, `pnpm run validate:static-export`, and `pnpm run check:seo`; test that both route trees exist and every public URL has a self-canonical and reciprocal alternates.
- E2E: set browser locale to English, verify initial navigation to `/en/`, verify explicit selection survives reload, and exercise one core trip/planning flow in English. Verify Spanish fallback and direct deep links.
- Accessibility: run Storybook's configured accessibility project for both locale providers; include keyboard and accessible-name checks for the language selector.
- CI remains green through existing lint, type-check, Jest, RLS, timezone, data-path guard, static-export, SEO, Storybook, Wrangler dry-run, and E2E jobs. No credentials are needed for localization tests.

## Risks and blockers

- HTML cannot select English from the HTTP `Accept-Language` header under this hosting topology. The issue criterion is therefore refined to browser-language detection after client hydration; a no-flash, header-based guarantee would require changing hosting architecture.
- Rewriting every first-party string is broad and can miss less-visible accessibility/error copy. Dictionary completeness and source scans should be acceptance gates.
- The current `public/_redirects` and SEO scripts assume unprefixed paths; migration must preserve old bookmarks and auth callback parameters.
- Legal translations need owner review before representing them as approved legal text.

## Acceptance checklist

- [ ] The export contains at least two languages and `validate:static-export` passes.
- [ ] A browser with `navigator.language` set to English reaches English content and an explicit language choice persists. (Refines the issue's `Accept-Language` criterion because the Worker cannot negotiate headers.)
- [ ] `check:seo` validates `hreflang` and there are no cross-language canonicals.
- [ ] E2E covers a critical flow in the secondary language.
